# 規格：獵取 regime 濾網 + fail_fast 的模擬（研究端 → 產品端，2026-08-26）

> 使用者要在產品端開模擬帳戶跑這個。研究端的供給側已完成，本文是實作
> 規格。研究記錄：flow_system `TODO.md §0.58 / §0.59`。
>
> **先講定位，因為這決定數字怎麼用**（下方 §五 展開）：
> 模擬跑的是**執行管道**，不是 edge。§0.59 的判決一律用 shadow log。

## 一、為什麼要加這道濾網

§0.58 的分解（變體 B、core9、同為 level 價、兩樣本不重疊）：

| 格 | 歷史 R | 前瞻 R | 格內差 |
|---|---|---|---|
| TREND_UP | +0.0221 | **−0.2254** | −0.2475 |
| NEUTRAL | +0.1011 | −0.0491 | −0.1502 |
| TREND_DOWN | +0.1076 | +0.1570 | +0.0495 |
| **RANGING** | **+0.0983** | **+0.0933** | **−0.0050** |

**主場（RANGING）兩期一致，崩的全在非主場。** 不是 edge 死了，是進錯
環境的代價變大了。只在主場開火的前瞻 meanR 是 **+0.0933** vs 全體
**−0.0102**，差 **+0.1035R**——你們項 G 的最佳出場變體是 +0.0078R，
**13 倍**。

## 二、供給側（研究端已完成，可直接用）

`GET /public/raid-pending` 每一筆多了 `regime_cell`：

```json
{ "symbol": "AVAX", "side": "LONG", "trigger_px": 7.4320,
  "stop_px": 7.0836, "risk_frac": 0.0469, "variants": ["A","B"],
  "regime_cell": "RANGING",          // ← 新增
  "expires_ts": 1787..., "expires_in_min": 303 }
```

`rules` 區塊也帶了 `home_regime: "RANGING"` 與四格清單，**不要在產品端
硬編這個字串**——研究端若改定義，跟著 rules 走才不會脫鉤。

四格取值：`RANGING` / `TREND_UP` / `TREND_DOWN` / `NEUTRAL`
（凍結 ADX(14) 25/20，TRENDING 再按同期 24h 報酬符號分向）。

**一個刻意的語意差**：端點的 `regime_cell` 是在 **sweep bar** 評估的
（那是你們可行動的時點）；研究端帳本用 **fill bar**（1~8 小時後，標籤
可能已變）。這個差異無害——你們驗管道、帳本定 edge，見 §五。

## 三、模擬要跑的兩條規則

**規則 1（濾網）**：`regime_cell !== rules.home_regime` 就跳過，
落 skip 原因 `regime`（沿用你們既有的 `_skip` 機制）。

**規則 2（fail_fast 出場）**：逐字照抄凍結定義
（`exit_variants.py:279`，原文為 `d==1` 即 LONG）：

```
每根 1h K 棒收盤時檢查：
  LONG  且 close <  trigger_px  → 出場
  SHORT 且 close >  trigger_px  → 出場
```

語意是「價格**收回**被掃穿的那一側 ⇒ 回踩論點已死，這根收盤就走」。

三個容易做錯的點：
1. **用收盤價，不是即時價。** 凍結定義是 bar close；用 tick 判定會提早
   觸發，那是另一條規則，模擬出來的數字不可比。
2. **比較對象是 `trigger_px`**（被掃穿的池位），不是進場價。武裝清單
   下發的 `trigger_px` 就是它，兩者在觸價進場時數值相同，但**日後不要
   改用實際成交價**——成交價含滑價，會讓門檻漂移。
3. 觸發後**這根收盤出場**，不是等下一根。

其餘不變：3.5×ATR 停損、8 小時上限、`risk_frac` sizing。

**建議做成兩個獨立開關**（`regimeFilter` / `failFast`），這樣模擬能跑
四種組合，之後歸因才分得開誰有效。

## 四、預期會看到什麼（先寫下來，免得事後解釋）

- **筆數約降到 45%**（RANGING 在前瞻樣本佔 45.3%）。這是**預期成本
  不是失敗**，寫在這裡是為了避免看到「訊號變少」就想放寬。
- 主場的 baseline 是 **+0.0907R**（全歷史 paired），fail_fast 再加
  **+0.0138R**（7/9 幣、兩半同號）。
- **TREND_UP 若被濾掉就用不到 `hold_4`**（那格唯一有效的變體，
  +0.0260R）。它是濾網 FAIL 時的備案，**不要同時上**。

## 五、【最重要】模擬數字能回答什麼、不能回答什麼

你們自己的 CLAUDE.md 已經寫死這條，研究端完全同意：

> 研究線回答「有沒有 edge」，產品端回答「執行管道撐不撐得住」。拿產品端
> 績效去確認策略等於同一筆資料算兩次。

| 模擬**能**回答 | 模擬**不能**回答 |
|---|---|
| 濾網有沒有正確擋單（比對 shadow log 的 regime_cell） | 濾網有沒有 edge |
| fail_fast 實際觸發率與滑價 | fail_fast 值不值 +0.0138R |
| 兩個開關的實作正確性 | §0.59 該不該上線 |

**§0.59 的判決一律用 shadow log**（研究端記帳、無執行成本、樣本完整）。
研究端已於今日讓 shadow log 開始記 `regime_cell`，新 fills 從此帶標籤。

## 六、一條紀律，請一起守

§0.59 是**看過現有 forward 樣本之後**提出的，所以那批樣本已經用掉，
**不得再當證據**。判決只能用 **2026-08-26 之後**新累積的 fills
（研究端 30 天 / n≥150 的守門）。

這正是變體 C/D 踩過的坑：凍結時統計量最漂亮的 D，forward 最慘。
**模擬跑得好看不構成上線理由**——上線看 shadow log 的判決。

## 七、與十月總驗的關係（一個取捨，使用者已知情）

產品端一旦改規則，執行成本資料會混進兩種規則（濾網前 / 濾網後）。
建議在 `raid_trades.jsonl` 每筆記下當時的開關狀態（`regimeFilter`、
`failFast` 兩個布林），十月總驗才分得開。
