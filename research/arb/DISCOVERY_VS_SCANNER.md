# 預註冊：新聞/LLM 發現層 vs 掃描器（2026-09-04 登記，未開工）

> 使用者：「我正在評估這個方法會不會比直接的掃描器好，畢竟讀到錯誤資訊系統就會有
> 風險。」——這是實證問題，所以寫成可判定的形式。**先寫起來，之後再決定要不要開。**

## 為什麼不是「哪個比較好」

兩者回答不同問題、犯不同的錯：

| | 掃描器 | LLM／新聞 bot |
|---|---|---|
| 資料 | **直接讀簿口** | 讀別人寫的文字 |
| 產出 | 「4.1 bps、3bps 內 $151k」 | 「X 好像有機會」 |
| 錯誤型態 | 量測錯（單位、篩子、過期） | 解讀錯／幻覺 |
| **可重現** | ✅ | ❌ |
| **可查證** | ✅ 回去看簿口 | ❌ 主張不在簿口上 |
| 修好之後 | 永久 | 下次還會犯 |
| 盲點 | **看不到不知道存在的場館** | 慢（實測落後 API 6h） |

**實證兩則（2026-09-04 當天）**：
1. 掃描器的 12 個錯全部靠「數字物理上說不通」抓到（Bitget 深度 ÷10,000、
   Binance 188 個合約被篩子藏起來、GOLD 混三種發行商）。**儀器的錯有形狀。**
2. **這條線最貴的一次污染來自文字**：上游 README 的「Entropy 100% 返佣」讓五天
   的每個淨值算式都錯 3.4 bps，直到使用者貼帳戶頁截圖才發現。那不是 LLM 犯的，
   但**正是 LLM 會犯的那一類——只會更快、更多、更有自信**。
3. BWEnews 對 Binance 期貨上市**比交易所 API 慢 6 小時**（GPRO 13:45 開始交易、
   20:30 才貼）。**API 已經吐出來的東西，讀文字一定較慢。**

## 風險大小完全取決於接線位置

```
安全：  bot（發現） → 掃描器的場館清單（設定） → 量測 → 凍結判決 → 引擎
危險：  bot → 引擎
```

- 接發現：bot 說錯 → 掃描器量了發現沒有 → 成本是幾天無用錄製。**下游接得住。**
- 接執行：**下游沒有任何東西接得住**——繞過收斂關、深度關、成本七桶、凍結判準，
  而且**可被餵**（公開文字驅動下單＝任何人都能貼餌）。

**硬規則（若將來要開）**：bot 的輸出只能是**問題不是答案**，只能改**掃描器的場館
清單**，永遠不得進入下單路徑或 sizing。
- ❌「NBIS 在 io↔lighter 有 14 bps」（它算不出來，算出來也不能信）
- ✅「Polymarket 上線永續，把它加進掃描清單」

## 兩週對照測試（判準事前寫死）

平行跑兩週，數三個數字：

| # | 量什麼 | 判準 |
|---|---|---|
| D1 | bot 報出、**掃描器沒有覆蓋**的機會數 | **=0 → 沒有貢獻**，掃描器已覆蓋，不開 |
| D2 | D1 之中，**經掃描器量測後真的存在**的比例 | **<50% → 成本是驗證假訊號的時間**，不開 |
| D3 | 掃描器看到、bot 沒報的數量 | 記錄值（量它的漏報，不當閘門） |

**開的條件**：D1 ≥ 3 且 D2 ≥ 50%。缺一不開。

**先寫下的預期**：D1 **不會是 0**——今天的 Polymarket 永續、Bitget rToken、
HIP-3 oracle 設計全部來自文字，掃描器一個都找不到。但它們的共同點是
**「哪裡開了新戰場」，不是「現在哪裡有 50 bps」**。所以我預期 bot 的價值集中在
**發現與風險**，不在價格。

## bot 該負責的四格（對照 COST_INVENTORY）

| 它報什麼 | 對應成本項 |
|---|---|
| 新場館／新產品上線 | 掃描器場館清單 |
| 費率／返佣政策變動（促銷到期） | R7 |
| 事故（逼空、暫停提幣、脫鉤） | O4／R1／R2 |
| 監管／下市 | R4 |

這四件都是「文字先於數字」——API 不會告訴你「Bitget 的返佣要停了」。
