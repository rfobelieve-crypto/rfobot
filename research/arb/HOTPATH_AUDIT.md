# 熱路徑審視：八條原則逐條對帳（2026-09-04）

> 使用者給的八條高頻套利系統原則。**先照第 8 條做——量了再說，不憑推論。**
> 本檔逐條標「適用／部分適用／不適用」，每一條附**我們的實測數字或程式碼位置**，
> 不寫沒有證據的評語。

## 先校準一件事：我們不是高頻系統

| 量 | 我們的實測值 |
|---|---|
| 機會壽命（收斂中位） | **5–15 分鐘** |
| 掃描週期 | 180 秒 |
| 錄價週期 | 60 秒 |
| 本機到場館往返 | 32–95 ms |

**所以第 1 條「能否穩定地更快下單」對我們是部分適用**：我們早就量過，
吃延遲的**不是進場而是撤單**（掛單模式下價格動了要在被吃掉之前撤掉）。
進場慢 100 ms 不會錯過一個 5 分鐘的機會。

**但第 3、5、6、7、8 條與頻率無關**——它們講的是「不要蓋一個脆弱的系統」，
在任何頻率下都成立。下面逐條對帳。

---

## 逐條對帳

### 1️⃣ 核心不是公式複雜度，是能否穩定更快下單 —— **部分適用**

我們的瓶頸實測不在速度：帶 2–15 bps、深度 $19–500k、費率門檻 4.5–18 bps。
§1.06 的七桶成本裡**滑價與資金成本目前都是 0**（size 小於頂檔、持有 5–15 分鐘），
死因是**費率與深度**，不是延遲。

**但撤單延遲會變成逆選擇成本**（S5），那是 B3 maker 路徑上線後要量的第一件事。

### 2️⃣ 拆成熱路徑 ＋ 旁路 —— **適用，而且我們已經拆了一半**

| 元件 | 現況 |
|---|---|
| 引擎（掛/撤/吃/對帳/停） | 東京 VPS（規劃中） |
| 錄價、掃描、判決、發布 | 已經是獨立程序 |
| 儀表板 | Railway，唯讀、無按鈕 |
| **⚠ 錄價器（MinuteRecorder）** | **跑在引擎的同一個 event loop 裡**（`engine.py` `asyncio.create_task(self.recorder.run(...))`） |

**這是唯一一處熱路徑與旁路沒有分開的地方。** 見第 3 條的實測。

### 3️⃣ 熱路徑極簡：不做磁碟寫入、慢網路、重日誌 —— **適用，實測如下**

```
錄價 writerow + flush : 中位   6 µs   p95  12 µs   最大 139 µs
風控 sum(2 腿)        : 中位 0.50 µs  p95 0.50 µs
單次 log.info         : 中位 14.2 µs  p95 18.6 µs
```

**判讀（誠實版）**：
- 錄價的同步 flush **確實在事件迴圈上**，但成本是 **6 µs 中位／139 µs 最大**，
  而我們的決策週期是**分鐘**。以現在的頻率，這個抖動**測不出來也不重要**。
- **執行路徑上有 6+ 個 log 呼叫**（`log.info` 兩個、`error`／`warning`／`critical` 各若干），
  合計約 **40–90 µs**。同樣，相對 32–95 ms 的網路往返是 **0.1%**。
- **結論：以目前的頻率，第 3 條不構成問題——但它是「將來會咬人」的那一類。**
  真要往秒級取樣或 maker 快撤走，這兩處就要動（錄價移出迴圈、log 改非同步）。
  **現在不動**，理由是第 8 條（沒有量到問題就不要動大手術）。

### 4️⃣ 先做延遲預算 —— **適用，但我們的預算單位是分鐘不是微秒**

我們的「預算」其實已經存在，只是寫在別的地方：`staleness_sec=10`（簿口超過 10 秒
就不下單）、`settle_timeout=10`、`reconcile_sec=15`、`venue_probe_sec=30`。
**這些就是延遲預算**，只是刻度是秒。maker 路徑上線時要新增一格：
**撤單預算**（掛出到撤掉的容忍上限，作者 repo 用 5 秒）。

### 5️⃣ 風控在線且輕量、常數級開銷 —— **適用，且已經是**

`max_net_base` 的檢查是 `sum(v.position for v in venues)`——**兩腿，O(1)，0.5 µs**。
放在 `_maybe_hedge` 開頭。其餘守衛（`cap_usd` headroom、`orders_per_min` deque、
`is_fresh`）也都是常數級。**沒有一個守衛做 I/O 或網路呼叫。**

**這一條我們是合格的，而且是設計出來的不是碰巧**——B4 寫的時候刻意不查 DB、
不寫檔、不呼叫交易所。

### 6️⃣ 先穩定低延遲，再追極限；抖動比平均更危險 —— **適用，而且我們有反例**

實測抖動：錄價 flush 中位 6 µs 但**最大 139 µs（23 倍）**。
網路那側更明顯：OKX 中位 95 ms、**最慢 161 ms**；Lighter 中位 32 ms、**最慢 85 ms**。

**這正是為什麼 `staleness_sec` 這種「絕對時限」比「平均延遲」更該存在**——
它擋的是尾巴，不是均值。

### 7️⃣ 必須支援降級：旁路壞了不影響交易、單一交易所異常可隔離 —— **適用，已有一半**

| 降級能力 | 現況 |
|---|---|
| 單一場館 API 掛掉 | ✅ 連 3 次抓不到部位 → `venue_down`，**只暫停該場館**，每 `venue_probe_sec` 探測 |
| 場館被限流 | ✅ `_mark_limited` + `rate_limit_pause_sec`，排序時降級 |
| 簿口過期 | ✅ `is_fresh` 擋下單與對沖 |
| 差額失控 | ✅ `max_net_base` HALT（今天加的） |
| **錄價器掛掉** | ⚠ **未驗證**——它在同一個 loop，如果它拋例外會不會帶掉引擎？ |
| 儀表板掛掉 | ✅ 結構上不可能影響（唯讀、下游） |

**⚠ 這是本次審視找到的唯一新缺口**（見下）。

### 8️⃣ 不要全量重寫，先 profiling —— **適用，本檔就是**

上面每一個數字都是剛才量的，不是估的。**結論是：不需要動大手術。**
熱路徑的成本在微秒級，而決策週期在分鐘級——**現在重寫是解一個還不存在的問題**。

## 本次審視找到的唯一新缺口

**G5：錄價器與引擎共用事件迴圈，且它的失敗路徑未驗證。**

`engine.py` 用 `asyncio.create_task(self.recorder.run(self.stop), name="recorder")`
把錄價器掛進同一個 loop。第 7 條說「旁路壞了不影響交易」——
但如果 `MinuteRecorder.run` 拋出未捕捉的例外，這個 task 會**靜默死亡**
（asyncio task 的例外若無人 await 只會在 loop 關閉時印出來），
而引擎會繼續交易、**以為錄價還在跑**。

這是這個專案認得的老病：**進程活著、功能死亡**（mistake.md 2026-04-22 那一族）。

**成本很低的修法**（列入 B4 的第二項，不是現在動）：
給錄價 task 加一個 done-callback，例外時 `log.critical` 並設一個
`self._recorder_dead = True` 旗標，**在狀態行印出來**——不停交易（旁路壞不該停熱路徑），
但**要看得見**。

---

## 對接下來工作的影響（三件事）

1. **B4 剩下四個開關照 O(1) 寫**——不查 DB、不寫檔、不呼叫交易所。這一條已經是
   B4 第一個開關的做法，繼續照做。
2. **加 G5 的錄價 task 存活旗標**（第 7 條）——比剩下的開關更接近「已知缺口」。
3. **不動熱路徑的 I/O 與 log**（第 8 條）——量到的成本是微秒，週期是分鐘。
   等 maker 路徑或秒級取樣上線後**重量一次**再決定。
