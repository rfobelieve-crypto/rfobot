# X4 — 每所 $50、一週小額實盤規格（2026-09-04 凍結，跑之前寫死）

> **這一週的產出不是損益，是把成本名冊裡的假設換成量測值。** 判準寫在下面，
> 事後不放寬。做完照同一份清單交代結果，包含沒做到的項目與原因。
> 對應：`COST_INVENTORY.md` 的 X4、`cost_model.py` 的 ASSUMED 欄位。

## 0 為什麼是 $50

最小下單名目（2026-09-04 查證）：OKX 股票永續 $1.9–7.7、Bitget $5、Binance $5
（BTC $50）、HL $10。**$50 一所開得了單，而且 1× 槓桿 → 清算風險消失。**

$50 **不是賺錢尺寸**，是驗證尺寸：毛利 4 bps × $50 ＝ 每筆 $0.02。
賺錢尺寸由兩個約束夾出來（薄側深度定上限、提幣費攤提定下限），約
每所 $500–1000、每筆 $200–400——**那是這一週之後的事**。

## 1 範圍與硬界線

- 配對：**只做兩個**——`NBIS`（io↔lighter，深度最好的股票永續）與
  `NVDA_LL`（lighter↔lighter-rh，兩腿零費對照）。不加碼、不換配對。
- 每所餘額上限 **$50**，總曝險上限 **$300**（六個帳戶）。輸光即結案，不補錢。
- **絕不重平衡**：$1 提幣費攤在 $50 上是 2%。存貨漂到一邊就停該配對——
  這件事本身是要量的（見 M6）。
- 資金與交易路徑**完全獨立於 V7／獵取**（CLAUDE.md 第 4 線隔離）。
- 產品端（jarvis）**只顯示不執行**（見 §3）。

## 2 要量的七件事，每件一個判準

| 代號 | 量什麼 | 方法 | 通過的樣子 | 換掉哪個假設 |
|---|---|---|---|---|
| M1 | **帳單上的真實費率** | 每所各一筆最小單，讀成交回執的 fee 欄位 | 與 `fees.py` 差 <0.5 bps；不符就以回執為準改表 | F1–F8 全部 |
| M2 | **掛單成交率** | 一腿掛在最佳價、5 秒未成交即撤，記 100 次的成交/撤單比 | 成交率 ≥30% → 掛單模式可用；<10% → 這條路關掉 | F9、S5 |
| M3 | **逆選擇** | 掛單成交後 60 秒的中價漂移（相對成交價，帶符號） | 平均漂移 > −1 bps → 沒有被系統性挑走 | S5 |
| M4 | **兩腿延遲** | 第一腿確認成交 → 第二腿確認成交的牆鐘毫秒 | 中位 <2 s、p95 <10 s | O5、T3 |
| M5 | **對帳與資料過期** | 每 15 秒對兩腿倉位；故意讓一腿的行情延遲 >10 秒，確認引擎**停**而不是補單 | 觸發即 HALT，且不下任何修正單 | O7（必修項） |
| M6 | **存貨漂移速度** | 記每個配對做到「一邊滿」需要幾筆 | 記錄值本身即產出；<5 筆代表單邊性太強 | C3、T4 |
| M7 | **劃轉真實成本** | 收工時做一次 HL→Lighter、CEX→HL 各一次劃轉，記費用與到帳分鐘 | 記錄值本身即產出 | T1、T2 |

**收工判準**：七件都有數字（或明寫哪件沒做到、為什麼）→ 用量到的值重跑
`cost_model.py`，看「量到%」從 43% 升到多少，以及哪些配對翻正。
**這一週不判斷這條線的存廢**——那是 §0.75 家族時鐘與 §1.05 的事。

## 3 速度：Railway 能不能套到利（2026-09-04 實測）

本機（台灣）到各場館的往返延遲，各 5 次取中位：

| 場館 | 中位 | 最快 | 最慢 |
|---|---|---|---|
| Lighter | **32 ms** | 26 | 85 |
| Lighter-RH | 65 | 28 | 108 |
| Binance | 65 | 63 | 88 |
| HL | 80 | 58 | 85 |
| Bitget | 88 | 73 | 115 |
| OKX | 95 | 87 | 161 |

**這條策略不是微秒賽局，但也不能放在美國。** 三個數字決定架構：

1. **機會的壽命是分鐘**：收斂中位 5–15 分鐘（判決程式量到）。進場慢 100 ms
   不會錯過。
2. **真正吃延遲的是撤單**：掛單模式下，價格動了要在被吃掉之前把單撤掉。
   撤單來回 200 ms vs 60 ms，差的那 140 ms 就是 M3 要量的逆選擇成本。
3. **Railway 沒有東京區**（US/EU/新加坡）。新加坡到 HL/OKX 約 30–60 ms，
   到 Lighter 系（美國）約 150–200 ms；美國區則相反。**沒有一個區同時靠近
   兩條腿**——而兩條腿都要撤得快。

**結論：執行引擎不放 Railway。** $8–20/月的東京 VPS（多數場館的機房在那）
一台就解決，順便解 Polymarket 的 DNS 封鎖（§1.05）。

## 4 儀表板：放 Railway，但只顯示不執行

沿用這個 repo 已經在跑的那條線（`agent-boundary.md`：資料單向流動）：

```
東京 VPS（執行引擎 + 錄價）
   → 每 30 秒寫 arb_live_* 表（MySQL）
   → agent-mcp 的 /public/arb-live（唯讀）
   → jarvis 儀表板頁
```

**產品端一行交易程式都不寫**，跟現在的 `/public/arb-status` 完全同款。
儀表板要有的（全部是引擎已經在算的東西，不新增計算）：

- 每個配對：當前帶、扣七桶後的淨、深度分級、離判準還差多少
- 每筆交易：兩腿成交時間差（M4）、掛單成交/撤單（M2）、成交後漂移（M3）
- 存貨：各所餘額與偏斜（M6）、離「一邊滿」還有幾筆
- 守衛狀態：資料年齡、對帳結果、HALT 原因（M5）——**紅燈要能一眼看到**
- **公開面規則照舊**：只出百分比、方向、時間；不出美元餘額與部位金額

## 6 三層架構：引擎／控制／儀表板（2026-09-04，回答「套利放用戶端好嗎」）

### 別人怎麼跑（我們實際讀過的兩份一手資料）

- **那對兄弟**：機器人跑在伺服器上，「我弟幾乎每天推 code，我一直依市場調參數」。
  控制是**改參數＋重啟**，不是點按鈕。他們的 $1.1M 事故是機器人自己失控 15–30
  分鐘，人是**事後**手動平掉 $120M——**沒有任何按鈕救得了那 15 分鐘，只有引擎
  自己的守衛救得了**。
- **entropy-arb 作者**（我們跑的錄價程式）：伺服器建議**東京 AWS**；控制面他列的是
  IP 白名單＋金鑰登入、**TG bot 一鍵減倉／暫停**、每筆成交後自動對兩腿、
  「預期成交價 vs 實際成交價」偏離監控、近 X 分鐘損益異常告警。

**共同形狀：引擎在靠近場館的伺服器上自己跑，人透過一個很小的命令通道介入，
觀察走另一條路。沒有人把執行迴圈放在網頁應用裡。**

### 為什麼不放用戶端（jarvis）

1. **延遲**：實測沒有任何 Railway 區同時靠近兩條腿（§3）。
2. **迴圈不能等 HTTP**：套利要在同一個 tick 內決定「掛/撤/吃/停」。放進 web 應用
   等於把交易迴圈綁在請求生命週期與部署重啟上——jarvis 每次部署有 1–2 分鐘盲區
   （CLAUDE.md 08-21 已記，那是 V7 真錢的已知風險）。
3. **爆炸半徑**：jarvis 上有其他用戶的錢。套利是第 4 條線，CLAUDE.md 寫死
   「永不 import 交易路徑、資金完全獨立」。放進去就違反這條。

### 三層，各自的職責與不可越界的地方

| 層 | 在哪 | 負責 | 絕不負責 |
|---|---|---|---|
| **引擎** | 東京 VPS | 掛/撤/吃/對帳/停。**所有 kill switch 寫在引擎裡** | 不等人、不讀網頁、不接受「建議」 |
| **控制** | TG bot（已有通道）＋ 落地的命令檔 | 四個動詞：`pause`／`resume`／`flat`（只平倉不停機）／`size` | 不做參數微調、不做下單 |
| **儀表板** | jarvis（Railway） | **唯讀**。看得到引擎在想什麼 | **一顆按鈕都沒有** |

### 儀表板不是控制台——這個專案有疤

`/okx-admin/heal` 曾經是個 GET 端點，被**連結預覽的預抓**帶著 `confirm=YES`
觸發，把一筆活著的真錢部位在 DB 裡歸零，造出孤兒倉（mistake.md 2026-06-07，
而且是第二次）。教訓寫在那裡：**任何會改變真實交易所狀態的操作，絕不可掛在 GET；
破壞性操作＝POST＋token＋執行前先核對真實外部狀態。**

所以控制通道的規格是：
- **四個動詞就好**，每個都**冪等**（重送兩次結果相同）
- **儀表板掛掉時仍然要能用**——所以它不經過儀表板，走 TG（或 SSH）
- `flat` **只平倉不停機**、`pause` **只停新單不平倉**——分開，因為出事時你要的
  往往只是其中一個（jarvis 的「一鍵全停」就是這個設計：只停策略、不平倉）
- 引擎收到命令前後各推一則 TG，**做了什麼要看得見**

### 引擎必須自己決定、不准等人的事

CLAUDE.md 的老規矩：**hard rules 寫進程式碼，不靠紀律**。這一週的引擎至少要有：
資料過期就停（M5）、兩腿差額超過上限就停、單配對倉位上限、日損上限、
連續錯誤 N 次就停。**這些不是儀表板上的開關，是引擎啟動時就讀死的常數。**
那對兄弟的 15 分鐘證明：等人按按鈕的守衛等於沒有守衛。

## 7 憑證：每個場館要什麼、風險等級不一樣（2026-09-04 查證）

**讀行情不需要任何憑證**——掃描器現在同時讀 10 個場館的公開簿口，零金鑰。
要憑證的只有「下單」與「讀自己的成交」。

| 場館 | 認證方式 | 能不能限制成「只能交易、不能提幣」 | 現況 |
|---|---|---|---|
| HL 主場 ＋ 所有 HIP-3 dex（io/xyz/para/mkts） | **錢包私鑰**簽 EIP-712；**同一把 key 通吃所有 dex**（帶 `dex` 參數） | **可以**——用 **API wallet（agent wallet）**：能下單撤單，**永遠不能提幣或轉帳**。官方文件明載 | `venue_hl.py` 已實作（作者的碼，待逐行審） |
| Lighter ／ Lighter-RH | 帳號索引 ＋ API key 索引 ＋ API 私鑰（自家簽章，要它的 SDK） | 是它自己的 API key 體系，非錢包主鑰 | `venue_lighter.py` 已實作 |
| OKX ／ Bitget | API key ＋ secret ＋ **passphrase** | **可以**：勾選只給「交易」不給「提幣」＋ **IP 白名單** | **未實作**（新工作） |
| Binance | API key ＋ secret（無 passphrase） | 同上 | **未實作** |
| Polymarket | 錢包（Polygon）＋ CLOB 認證 | 待查 | 本機連不到（§1.05） |

### 三件會影響安全設計的事

1. **DEX 腿與 CEX 腿的金鑰風險不對稱。** CEX 的 key 可以砍成「只交易、不提幣、
   綁 IP」，外洩最多被亂交易；錢包私鑰**本身就是錢**。
   **解法是 HL 的 API wallet**：授權一把只能下單撤單、不能提幣的子鑰——
   這把「DEX 腿風險等於 CEX 腿」拉平了，是上線前必做的一步，不是選配。
2. **兩條 Lighter 鏈現在共用同一組憑證**（`config.py` 兩處都讀
   `LIGHTER_ACCOUNT_INDEX` / `LIGHTER_API_KEY_INDEX` / `LIGHTER_API_PRIVATE_KEY`）。
   mainnet 與 RH 是**不同的鏈、不同的帳號**——`NVDA_LL`（兩腿都是 Lighter）
   一定要兩組。**這是上線前必修的設定缺口**，錄價階段看不出來因為它不簽單。
3. **帳戶隔離**：CLAUDE.md 已經為了共用帳戶付過兩次代價（06-05、07-27 手動爆倉）。
   套利用的錢包／子帳戶**只放這條線的錢**，不與 V7／獵取／個人資金共用。
   HL 用獨立錢包、CEX 用子帳戶。
