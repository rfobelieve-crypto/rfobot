# 一個排序指標看不見的病：解碼把做空訊號鎖死了三個月

我的交易系統有一條規則：模型輸出一個連續的預測值，解碼層拿它跟自己過去
500 根的預測比排名，落在最高 2.5% 就發做多訊號，最低 2.5% 就發做空。

這個設計很常見，也很合理——它自動適應模型輸出的尺度變化，不需要人工調
門檻。它跑了三個月，每個月的例行復驗都通過。

然後有一天我發現，做空訊號的觸發門檻，**低於這個模型史上輸出過的最低值**。

不是「很少發」，是**算術上不可能發**。

---

## 一、症狀：一個怎麼看都像運氣的偏斜

模型重訓後我盯著訊號紀錄，發現部署以來是 **9 個做多、0 個做空**。

第一反應是「小樣本」。九次拋硬幣全正面的機率是 1/512，不算太離譜。而且同
期市場確實在漲——模型看多，也許只是它對了。

但一算就不對：那三天實際上漲的 K 棒只有 46%，模型卻有 74% 預測往上。而且
更關鍵的是，**重訓前後這個偏斜完全沒變**，都是 +28 個百分點。重訓是換了一
個全新的模型，如果偏斜來自模型，它應該會變。它沒變，代表病不在模型。

## 二、真相：不是機率問題，是算術問題

把數字攤開：

```
模型上線後的輸出範圍        [-0.001480, +0.002425]
做空側最寬鬆的觸發門檻       -0.001786    ← 比模型史上最低值還低
能觸發做空的 K 棒數量        0 / 74
```

門檻落在模型構不到的地方。做空訊號不是很少，是**不存在**。

原因在那個 500 根的比較基準（buffer）裡裝的是什麼。它裝的是模型在**自己訓
練資料上**的預測，平均值 −0.000005；而模型上線之後實際輸出的平均值是
+0.000716——**偏了 0.6 個標準差**。整個比較基準往下錯位，於是做空側的切點
被推到分佈之外。

## 三、為什麼是三個月，不是幾天

這是我一開始判斷錯的地方。我以為這是重訓後的暫時現象：buffer 是滾動的，
新的預測會慢慢把舊的種子擠掉，三週左右自己會好。

錯了。buffer 的持久化路徑是**容器內的一個檔案**，而這個服務每天部署 2–10
次。雲端平台的容器檔案系統是暫存的——**每一次部署，buffer 都被重置回程式
碼倉庫裡那份訓練集種子**。

它從來沒有真的長成 live 分佈過。「暫時的偏差」因此變成「每天重演的常態」。

這一條我認為是整件事最值得記的：**任何滾動狀態（暖機緩衝、校準參數、統計
基準）都不能存在容器檔案系統裡**。它不會報錯，它只會安靜地在每次部署時回
到出廠設定，而出廠設定正是你以為早就被輪替掉的那個東西。

## 四、四道關卡為什麼全部漏掉

重訓時我自己寫了四道驗收關卡。四道全過，而病就在關卡看不見的地方：

**第一道量的是離散度比值**（新舊 buffer 的標準差比 0.78，落在允許區間）。
比值對「整體平移」完全免疫——這跟排序指標（IC、AUC）對水平漂移全盲是同一
種病：**你選的度量在數學上就測不到你要防的那件事**。

**第二、三道是在訓練窗上重放的。** 而模型在訓練窗上「對中」是最小平方法的
建構保證，不是一個可以拿來檢驗的性質。在訓練資料上驗證校準，等於零證明力。
（我的合作者當天就指出「但這是 in-sample 的資料」，我沒把它當成擋關條件。）

**第四道沒有任何一關問那個唯一該問的問題**：切點落在模型輸出得到的範圍內
嗎？

這個問題是純算術的。它的答案不是機率、不是統計顯著性，而是確定的是或否。
一問就會發現，而我沒問——因為我在檢查「分佈的形狀對不對」，沒有檢查
「兩者有沒有交集」。

## 五、修法

1. **buffer 改從資料庫重建**，開機時讀最近 N 筆真實生產預測。容器重啟不再
   洗掉它，而且它依定義就是 live 分佈——**兩側可達性從「祈禱」變成建構上的
   保證**。
2. **暖機期不發訊號**，而不是退回固定門檻。重放顯示暖機期正是偏斜最嚴重的
   地方（五個重置點分別是 53:17、64:4、54:20、65:2、43:5）。代價是重訓後約
   四天的靜默，換掉四天的單邊訊號。
3. **新增一道可達性關卡**：直接計算「兩側各有幾根 K 棒構得到切點」，兩側各
   至少要有一根。這關是純算術，過不了就是確定會出事，不是風險。

## 六、過程中做對的一件事

我寫了一支重放工具來排序修法。第一版跑出來的結果說 8 月是 14:18（接近平衡），
與實際觀察到的 9:0 矛盾。

**我沒有解讀它，先去查產生它的程式碼。** 漏了「部署會用種子取代 buffer」這
個動作，所以重放讓種子早就被輪替掉了。修好之後從同一個重置點重放得到 11:0，
病灶重現，工具才拿來排序修法。

這條後來寫死成一條規矩：**重現不了已知病灶的工具，不能用來排序修法。** 一個
沒有在已知答案上驗證過的診斷工具，比沒有工具更危險——因為它會給你一個看起
來乾淨、可發表的錯誤結論。

## 帶得走的三句話

1. **任何「跟自己的歷史比排名」的機制**（滾動分位數、z 分數、分位門檻）都隱
   含「分佈平穩」的假設。上游一漂，這個假設必然壞掉，而**排序類指標測不到
   它**——監控必須同時看排序和刻度。
2. **必須有一關直接問「切點落在被判斷對象的輸出範圍內嗎」**。比值、離散度、
   rank 指標全都測不到這件事，而它是唯一一個失效時是確定、而非機率的環節。
3. **滾動狀態不可以存在容器檔案系統**。每次部署都會重置，而重置回的是寫進
   程式碼倉庫的那份——於是「暫時的偏差」變成「每天重演的常態」。
